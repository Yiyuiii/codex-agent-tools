Windows 双控制通道补充规格

你只需要判断一个问题：是否把失败的“单 fd3 双向 half-close”改为 fd3 命令输入 + fd4 事件输出，并同时闭合发现的 Windows handle 与环境继承边界。

已经由机器确认的事实

普通双向通信成立

Node 20.20.2 上，真实 C# _get_osfhandle(3) 完成 CONFIG/ACK/READY 与 PING/PONG。

write-half-close 不成立

Node 调用 stdio[3].end() 后，Windows libuv 关闭该 pipe 两端，Node无法再收到terminal。

批准规格要求任一锁定Node版本失败即硬停，因此22/24未运行、Task 3未开始、失败代码未提交。

推荐方案

通道唯一职责关键效果
fd3Node → helper：LAUNCH_CONFIG / TERMINATEfd3 EOF仍触发session_shutdown和Job清理
fd4helper → Node：READY / ERROR / EXITfd3关闭不再破坏terminal证据

两个通道仍由同一个固定.NET Framework 4.8 helper承载，不增加服务、native addon、PID lookup或direct-spawn fallback。

批准时同时闭合的四个边界

  1. 名称边界：禁止项目管理或可重连的named pipe；承认Windows libuv内部会创建有名称的单实例pipe。项目不暴露名称、不接受名称参数、不提供重连；同用户恶意进程不在当前威胁模型，若要防御必须重新设计。
  2. target继承：helper清除fd3/fd4继承位，创建target时固定cbReserved2=0、lpReserved2=NULL，HANDLE_LIST仍恰好只有0/1/2。
  3. 环境闭包：显式携带libuv可能从父环境补入的11项Windows required variable；缺失或漂移在spawn前失败，避免隐式父值穿透。
  4. Node支持：Windows native route只支持major 20/22/24；其它major固定fail closed。发布证据仍使用精确20.20.2、22.23.2、24.18.1。

不会改变的核心保证

  • target在第一条用户代码前通过JOB_LIST原子归入inner Job；禁止post-create assignment。
  • helper是唯一Job handle owner；target只继承0/1/2。
  • 无PID reopen、WMI、taskkill、全机扫描、named-pipe或direct-spawn自动fallback。
  • terminal缺失、重复、乱序、Job未归零或helper异常退出均fail closed。
  • 不对Kimi、Pi或任何外部CLI增加默认或持久化的执行资源限制。
  • Tasks 1–14仍不调用真实模型、不改活动配置/插件、不发布。

批准后的第一步仍是硬门禁

先重新执行replacement Task 2，而不是进入Task 3：同一个锁定C# probe必须在三版Node上证明fd3/fd4独立、无串线、fd3 EOF后fd4 terminal、parent/helper crash、动态nonce、无Job/target/env读取以及失败清理不掩盖primary error。父进程牺牲测试只有在外层先验证nonce绑定的observer已武装和carrier ready后才允许退出；未武装、watchdog、超窗或迟到EOF都只能失败。任一版本失败仍立即停止。
