机器现在无法回答的问题

现有 evidence 只保存命令数量与“是否看到精确 git status --short”，没有保存第一条写入命令的脱敏分类，也没有关联工具结束事件。 因此不能区分以下四种情况：

  1. 模型跳过了写入命令；
  2. 模型改写或包裹了命令；
  3. 精确命令已经发出，但工具返回错误；
  4. 命令成功写入后，后续动作又删除了文件。

diagnosticCount=0 不能排除工具错误，因为 Pi 的 tool-level error 当前没有进入 adapter diagnostics。

三个方案

方案 内容 优点 缺点
A：只记录命令匹配 保存写入命令的来源及 exact / trim_only / embedded / other。 改动最小。 若看到 exact 但文件仍缺失，仍无法判断工具错误还是后续删除，可能再浪费一个真实批次。
B：完整生命周期脱敏诊断（推荐） 在 A 的基础上，按内部 tool-call ID 关联开始与结束事件，只持久化 success / error / missing / unknown 结果枚举。 一次新 evidence 即可区分主要失败层；仍不保存命令、ID 或输出正文。 需要同时加固 Pi event sanitizer、内部 observation folding、producer 与 verifier，TDD 面更大。
C：立即改提示词 缩短或重写当前 Node + Base64 指令。 若失败只是模型偶发遵循问题，可能提高下一次通过概率。 当前没有证据指向提示词缺陷；同一合同已有两个同批通过反例，属于猜测性修复。

推荐设计：方案 B

  1. 内部事件层：Pi 的超大工具结束事件仍保留非秘密 isError；普通事件保持现状。按 tool-call ID 折叠开始与结束事件，冲突或缺失形成 unknown / missing，不猜测成功。
  2. 资格 producer：Pi delegate 的内部 observer 必须恰好回调一次；沿用当前 compatibility 策略，不改变公开 commandsRun 或历史 commandCount 语义。
  3. 脱敏 evidence：新增可选 writeCommandObservations。每项只含 source、match、outcome 三个闭合枚举；禁止 command、hash、rawInput、 tool-call ID、cwd、模型正文和工具输出。
  4. 严格 verifier：历史 evidence 缺字段仍通过；新字段出现时只允许当前 four-llm-v1 的 Pi delegate schema v3，检查普通数组/对象、精确键、枚举、最多 256 项和计数一致性。
  5. 验收中立：新字段只用于诊断。结果文件、唯一文件范围和精确 git status --short 仍决定通过；不把命令 start 或 tool success 冒充最终文件成功。
本设计明确不做：不修改提示词，不放宽 validator，不改变模型、provider、route、credential、 retry/fallback，不改 manifest/checkpoint/qualification plan，不回填历史 JSON，不修改公开 MCP 结果。
